# 开饭 · 产品需求文档（PRD）

> 版本：v0.2（已根据用户反馈修订）
> 文档定位：定义产品做什么、不做什么、做到什么程度。所有功能的具体实现方式在《技术文档》中展开。
> 主要变更：补充菜品卡片视觉规范、教学页面布局/字号/按钮规范、视觉风格锁定、决策记录更新。

---

## 1. 项目概述

### 1.1 一句话定位
**"开饭"** 是一款面向手机端的 AI 做饭助手：你把买菜订单截图丢给它（或直接说一句"想吃啥"），它会基于你家里**真实有的食材**，给你出 1–3 道家常菜方案，并一步步带着你做完。

### 1.2 核心价值主张
- **真实食材驱动**：菜谱严格基于用户上传/输入的食材，不会瞎编（米面油盐等基础调味默认有）。
- **完整执行闭环**：从出方案到一步步带做，不止是"给个菜谱"，而是"带着你做完"。
- **降低决策成本**：用户不需要想"今天吃什么、怎么搭配"，AI 给出一个营养均衡、口味多变的组合。

### 1.3 目标用户
- **核心用户**：工作繁忙但希望吃家常饭的年轻人（20–35 岁），平时用美团/京东到家/盒马等 App 买菜。
- **次要用户**：刚学做饭的新手、希望减少食材浪费的家庭主厨。

### 1.4 范围界定（v0.1 / MVP）
**MVP 包含**：账号登录、食材输入、菜谱生成、教学执行、结果页、缓存、异常处理。
**MVP 不包含**：社交分享、收藏菜谱、购物清单导出、营养详细报告、视频教程（先用图文）、菜谱社区。
> 上述非 MVP 项可在后续迭代讨论。

## 3. 功能详述

### 3.1 食材输入（多模态）

#### 3.1.1 输入方式
| 方式 | 行为 | 限制 |
|------|------|------|
| **图片上传** | 上传电商 App 买菜订单截图，支持多张 | 最多 5 张，单张 ≤ 10MB，格式 jpg/png/webp |
| **手动输入** | 文字输入想做的菜或有的食材 | 最多 500 字 |
| **语音输入** | 说出想做的菜或食材 | 单次 ≤ 60s，结束后转文字 |
| **混合输入** | 图片 + 文字 / 图片 + 语音 可组合 | 至少 1 种来源 |

#### 3.1.2 食材识别（多模态 AI）
- **识别目标**：从图片中识别出蔬菜、肉类、蛋类、海鲜、豆制品等**主要食材**。
- **不识别**：调料（米面油盐酱醋等基础调味品默认有）、包装袋品牌信息、订单价格、地址等无关信息。
- **识别失败**：返回识别结果为空时，进入 3.1.4 异常分支。

#### 3.1.3 食材安全阀门（核心约束）
> 这是产品最重要的原则之一：**绝不瞎编食材**。

- **基础调味默认清单**（默认用户家里有，无需识别、无需询问）：
  - 油、盐、糖、酱油（生抽/老抽）、醋、料酒、蚝油
  - 葱、姜、蒜、花椒、八角、桂皮、香叶（常见香料）
  - 淀粉、鸡精/味精（可选）
- **主要食材必须来源**：蔬菜、肉类、蛋类、海鲜、豆制品、菌菇 → **必须**来自用户上传的截图或输入文本。
- **菜谱中允许出现**：基础调味 + 已识别的主要食材。
- **菜谱中不允许出现**：截图/输入中没有的主要食材（哪怕是常见菜可能用到，如香菜、辣椒等）。
- **冲突处理**：若用户输入"想吃番茄牛腩"但截图里只有猪肉，则以**截图**为准，并提示"您的订单里似乎没有牛肉，是否使用猪肉？"，让用户确认。

#### 3.1.4 异常：食材占比不合理
**触发条件**：AI 识别出的"主要食材"占比 < 总识别内容的 30%（例如截图里全是调料、订单号、店铺名等）。
**处理方式**：
- AI 主动说明情况（文案："这张截图好像没看到具体食材哦，可能是调料或订单详情页～麻烦重新上传一张买菜清单的截图吧"）。
- 底部按钮从"换一批菜"切换为"上传买菜截图 / 手动输入 / 语音输入"三选一。
- 点击任一按钮直接唤起系统选图组件（图片）/ 键盘（手动）/ 录音（语音）。

> 此异常仅在**已尝试生成但识别失败**时触发；空识别（完全没识别出）走同样分支。

### 3.2 菜谱方案生成

#### 3.2.1 触发与调用
- 用户在输入页面点击"开饭"按钮 → 触发后端生成请求。
- 后端调用多模态大模型识别图片 + 调用意图理解模型解析用户文字/语音 → 生成 1–3 道菜 + 推荐碳水。

#### 3.2.2 菜谱设计原则
- **数量动态**：根据食材丰富度决定，1–3 道菜。
  - 食材少（≤3 种主要食材）→ 1 道菜
  - 食材中等（4–6 种）→ 2 道菜
  - 食材丰富（≥7 种）→ 3 道菜
- **营养结构（每套方案必须满足）**：
  - 至少 1 个蛋白质来源（肉/蛋/豆制品/海鲜）
  - 至少 1 个蔬菜
  - 推荐 1 个碳水（米/面/馒头/饼等）
- **口味多变**：同一套方案内不同菜口味应有差异（如一道红烧、一道清炒、一道凉拌），避免全是炒菜或全是红烧。
- **做法家常**：用最常见的家常做法（炒、蒸、煮、凉拌、炖），避免高难度技法（糖醋拔丝、复杂面点等）。
- **好吃健康**：少油少盐是默认，但**不能牺牲味道**——用户希望"好吃"是第一位的，健康是底线。
- **碳水默认逻辑**：
  - 若截图中识别出米/面/馒头等碳水 → 用识别结果
  - 若没有 → 按"中国家常"默认推荐（米饭为主，面条/馒头为备选）

#### 3.2.3 输出结构
```json
{
  "scheme_id": "uuid",
  "dishes": [
    {
      "dish_id": "uuid",
      "name": "番茄炒蛋",
      "main_ingredients": ["番茄", "鸡蛋"],
      "taste": "酸甜",
      "cooking_method": "炒",
      "difficulty": "简单",
      "estimated_time": "10分钟",
      "preview_image": "url",
      "preview_image_prompt": "（生成该菜品配图的 prompt 模板，见 3.2.3.1）"
    }
  ],
  "carb_recommendation": {
    "name": "米饭",
    "reason": "经典搭配"
  },
  "nutrition_summary": "本方案含蛋白质 X g，蔬菜 Y g，碳水 Z g"
}
```

#### 3.2.3.1 菜品卡片视觉规范

> 这是开饭最重要的视觉资产之一，配图直接决定用户对菜品的第一印象。

**整体布局**
- **左图右文**卡片式布局（竖向卡片，图片在左、文本在右）。
- 卡片样式：**白色底 + 阴影**（柔和投影，8px 圆角）。
- 卡片右侧有一个**箭头**（› 或 →），暗示可点击进入。

**配图（左侧）**
- **比例**：1:1 正方形。
- **背景**：**纯白色**（#FFFFFF，无任何装饰）。
- **拍摄角度**：**斜上方俯拍**（约 45°），类似餐桌记录的视角。
- **餐具**：使用**最优雅、最干净的简洁白色盘子**，参考高级餐厅摆盘风格。
- **花纹**：**禁止**任何花纹、图案、装饰性纹理，纯白餐具。
- **光线**：**真实摄影光线**——自然光为主，带柔和阴影；不能是平铺的 3D 渲染感或卡通插画。
- **食物呈现**：菜品居中、摆盘精致但不过度装饰，看得出"刚出锅"的新鲜感。
- **生成方式**：使用 **MiniMax image-01** 文生图模型批量生成，prompt 模板见技术文档。

**文字（右侧）**
- 顶部：**菜品标签**（菜名，字号最大，加粗）。
- 标签下方：**一句话描述**（如"酸甜开胃的家常经典"）。
- 描述下方：**预估用时**（如"约 10 分钟"），小字、灰色。
- 整体留白宽松，文字行高 1.5 倍以上。

**配图 prompt 模板（占位）**
```
{A dish name}, top-down 45-degree angle, served on a clean minimalist white plate,
pure white background, soft natural lighting with gentle shadows, professional food
photography, fine-dining presentation, no patterns or decorations, fresh and appetizing
```
> 实际 prompt 在技术文档中调优，需保证生成结果的视觉一致性。

**视觉一致性要求**
- 所有菜品配图必须保持**相同的盘子、相同的光线、相同的拍摄角度**，只换菜的内容。
- 必要时微调 prompt 关键词（如"same plate", "consistent lighting"）来约束模型。

#### 3.2.4 换一批菜
- **触发**：用户在方案页点击"换一批菜"按钮。
- **实现**：
  - 将**上一轮的菜名列表**作为"已出过"标签包裹在新的 prompt 中传给 LLM，强制要求避免重复。
  - LLM 必须输出**与上一轮不同的菜**（菜名、做法、口味都应有差异）。
  - 新方案仍需满足 3.2.2 的所有设计原则。
- **缓存交互**：
  - 当前展示的方案**已缓存**，返回菜单时**不重新请求**，直接展示。
  - 只有点击"换一批菜"才发起新请求。
  - 卡片渲染不能闪动（先出现再消失再出现），切菜单时直接显示已有内容。

#### 3.2.5 加载动画
> 描述的是"开饭"在思考时的视觉体验。

- **位置**：页面正中央。
- **状态 A：思考中**
  - 三个食材图标横向并排。
  - 每个图标不断循环变化为其他食材（如番茄 → 茄子 → 西兰花 → 番茄）。
  - 变化节奏：**形似游戏机滚轮**，原地翻滚感。
  - 动画下方文字：「开饭正在思考今天的菜谱」
- **状态 B：完成**
  - 三个图标**从上到下依次落停**：
    - 最上面的先停 → 变成某个具体食材
    - 中间的停 → 变成**同样的食材**（必须相同）
    - 最下面的停 → 变成**同样的食材**
  - 落停的食材是**随机的**（从本方案所有食材里随机抽一个），不要每次都是同一种。
  - 三个全部落停成同一个后，**菜品卡片从页面中间依次浮现**（每张卡片间隔约 150ms）。
- **素材要求**：食材图标由用户后续提供，建议提供至少 20 种常见食材的图标（番茄、鸡蛋、牛肉、土豆、西兰花等）。

### 3.3 教学执行（单步拆解）

#### 3.3.1 教学页面布局详细规格

> 单步单屏是核心交互。每一步独立一个屏幕，但允许**屏幕内纵向滚动**。

**从上到下的结构（页面骨架）**

```
┌─────────────────────────────────────┐
│  顶栏（固定浮层）                      │  ← 层级最高
│  ┌─────────────────────────────────┐ │
│  │  ‹   「番茄炒蛋」   ···         │ │  ← 中间是菜名作为页面标签
│  └─────────────────────────────────┘ │
│  进度条（固定浮层）                    │  ← 层级最高，分成几节
├─────────────────────────────────────┤
│                                     │
│  第一步 · 共 5 步                     │  ← 步骤序号，小字
│                                     │
│  腌牛肉                              │  ← 步骤大标题，字号最大
│  ─────────────                       │  ← 分割线
│                                     │
│  做法描述（可滚动区域）                │  ← 可上下滑动
│  牛肉切薄片，加入生抽 一餐勺，         │
│  淀粉 一茶勺，腌制 15 分钟。          │
│                                     │
│  ...（内容可继续）                    │
│                                     │
├─────────────────────────────────────┤
│  底部按钮（固定浮层）                  │  ← 层级最高
│  [上一步]            [下一步 →]      │
└─────────────────────────────────────┘
```

**顶栏（固定）**
- 左侧：返回箭头 `‹`（用于返回方案页或上一步）。
- **中间：菜名作为页面标签**（如「番茄炒蛋」），文字居中，字号适中。
- 右侧：更多菜单（···），点击展开"重新生成步骤""退出"等次要功能。

**进度条（固定）**
- 紧贴顶栏下方，**分成几节**（每节对应一个步骤），可显示当前完成度。
- 已完成的步骤用主色填充，未完成的步骤灰色。
- 当前步骤可用动画强调（如光晕、轻微脉动）。

**步骤序号文字**
- 进度条下方，**小字**：`第一步 · 共 5 步`（使用居中点 `·` 分隔）。

**步骤大标题**
- 步骤名称（如"腌牛肉"），**字号比正文大很多**（具体见 3.3.2 字号规范）。
- 标题下方一条**分割线**（浅灰色，1px）。
- 标题与正文之间留出舒适间距。

**做法描述（可滚动）**
- **不拆分"材料"和"做法"两个 tab**——**合并为一个滚动区**。
- 每一步做法里**直接在材料前加用量**。
- 用量表达**人话化**（不用克、毫升等精确单位），例如：
  - ❌ "盐 5 克，温水 300ml"
  - ✅ "盐 一茶勺，油 一餐勺，温水 小半碗"
- 常用参照物映射：
  - **一茶勺** ≈ 5ml（调料类：盐、糖、鸡精）
  - **一餐勺** ≈ 15ml（液体类：生抽、料酒、醋、油）
  - **一小把** ≈ 一把（葱花、姜末、蒜末）
  - **小半碗 / 大半碗** ≈ 100ml / 200ml（水、汤、液体）
  - **几滴** ≈ 2–3 滴（香油、麻油）
- 每个做法**尽量拆成 1–2 个句子**，避免长段落。
- **数字与中文之间必须有空格**（如"腌制 15 分钟"，不写"腌制15分钟"）。
- 内容可上下滑动查看完整描述。

**滚动行为（关键交互）**
- 做法描述区域**支持上下滑动**。
- **滚动时，顶部进度条和大标题区域保持固定**（CSS `position: sticky` 或 `fixed`），不会被内容覆盖。
- 顶部浮层（顶栏 + 进度条 + 大标题）层级最高，**始终位于内容之上**。
- **向上滑动时，步骤大标题丝滑缩小字号**（CSS transform 实现，过渡 200ms），给用户"看到了下一段"的视觉提示，但仍保持可读。
- **向下滑动回到顶部时，大标题恢复原字号**。
- 底部按钮区域**也是固定浮层**，始终在屏幕底部，**不被内容覆盖**。

#### 3.3.2 字号规范（特殊距离要求）

> ⚠️ 这是开饭最特殊的视觉约束之一，必须严格遵守。

**背景**：做饭时手机通常放在厨房的**窗台或桌子上**，距离用户的眼睛约 **60cm – 1m**。这个距离是一般 App 设计假定的 30–40cm 的 **1.5–2 倍**。因此正文和关键信息必须**比一般 App 大 1.5–2 倍**，否则用户做饭时看不清。

**字号基准（移动端 375px 设计稿）**

| 元素 | 一般 App 字号 | 开饭字号 | 备注 |
|------|--------------|---------|------|
| 步骤大标题 | 18–20px | **32–36px** | 字号最大，最关键 |
| 步骤序号小字 | 12–14px | **16–18px** | 不能太小 |
| 正文描述 | 14–16px | **22–24px** | 比一般 App 大 1.5 倍 |
| 按钮文字 | 14–16px | **18–20px** | 按钮可点击也要看清 |
| 提示/标签 | 12–14px | **16–18px** | 不要小于 16px |

**字号关系**
- 步骤大标题 ≥ 正文 × 1.5
- 正文 ≥ 提示文字 × 1.3
- 所有可读文字**不得小于 16px**

**行高与间距**
- 正文行高：1.6 – 1.8（比一般 App 的 1.4–1.5 更宽松）。
- 段落间距：1.5em 以上。
- 文字颜色：**深棕黑**（#2A2520 系），不要纯黑，对比柔和不刺眼。

#### 3.3.3 按钮规范

> 强调色要克制使用——亮橙色（主色）只用在极其必要的情况下，常规按钮用黑色或棕黑色。

**上一步按钮（次要）**
- 样式：**浅色半透明气泡按钮**。
- 颜色：白色 / 半透明白 + 浅灰描边。
- **宽度小**（约 30% 屏幕宽），靠左。
- 文字"上一步"，字号正常（按 3.3.2 规范）。

**下一步按钮（主要）**
- 样式：**实心按钮**，**宽度大**（约 60% 屏幕宽），靠右。
- 颜色：**黑色或棕黑色**（#2A2520），**不要用强调色（亮橙）**。
- 文字"下一步 →"，加箭头。

**视觉区分原则**
- 上一步（次要）vs 下一步（主要）= **弱 vs 强**的对比，但都**不用主色**。
- 主色（亮橙 #FF7A45）**仅在以下场景使用**：
  - 关键 CTA（如"开饭"启动按钮）
  - 错误/警告的强调（如食材识别失败）
  - 当前活动状态指示（如进度条当前节）
- **绝不在普通导航按钮上使用主色**。

**按钮位置**
- 屏幕底部固定浮层。
- 左右各一个，中间留出间距，整体不顶满屏幕边缘（左右各留 16–24px 内边距）。
- 按钮高度：48–56px（方便厨房场景下点击）。

#### 3.3.4 步骤设计原则
- 一道菜的所有步骤拆分到**单步单屏**：每一步独占一个屏幕。
- 每步包含：步骤序号、当前动作、所需时间、可能的小贴士。
- 步骤颗粒度：每步 30 秒 ~ 5 分钟可完成（切菜、起锅、加调料、翻炒、焖煮等）。
- **倒计时步骤**：如"上锅蒸 15 分钟""小火焖 10 分钟"，用户可点击开启倒计时。

#### 3.3.5 倒计时步骤
- **触发**：步骤卡片上显示"开始倒计时 [N 分钟]"按钮。
- **倒计时大卡片**（点击后出现）：
  - 顶部出现**全圆角大卡片**，背景色突出。
  - 卡片内显示：**倒计时名称（如"蒸鱼"）** + **大号倒计时数字（mm:ss）**。
  - 停留约 **3 秒**后，**丝滑位移动画**缩放至右上角，变为**小胶囊**：
    - 胶囊只显示**跳动的数字** + 倒计时名称（2–3 字）。
    - 数字每秒跳动一次。
  - 点击胶囊 → 反向动画缩放回大卡片（可以查看完整信息）。
- **多个倒计时**：
  - 多个胶囊**重叠展示**在右上角（最右是最近开启的，依次向左堆叠）。
  - 重叠数量超过 3 个时折叠为"+N"。
- **倒计时结束**：
  - **全屏浮层** + **摇晃的闹钟图标** + **超大"知道了"按钮**。
  - 用户点击"知道了"后浮层关闭。
- **持久化**（核心需求）：
  - 倒计时**不依赖前端计时器**：记录**结束时间戳**（epoch ms）。
  - 用户切到其他 App 再切回来 → 重新计算 `剩余时间 = 结束时间 - 当前时间`。
  - 即使关闭浏览器再打开（如手机锁屏后），时间依然准确。
  - 实现方式：localStorage（前端）。MVP 不做登录，所以**不需要**Redis 同步。

#### 3.3.6 顺手做推荐
- **触发条件**：倒计时步骤开启后，倒计时 > 1 分钟。
- **页面内容变化**：原步骤页主体变为"趁这个时间，可以顺手做：xxx"。
- **推荐原则**：
  - 必须是**当前菜谱其他步骤**中可提前做的（如"趁蒸菜的时候把牛肉腌上"）。
  - 必须**符合真实做饭逻辑**，不冲突（如不能推荐"切菜"因为已经在倒计时阶段了）。
  - 每次只推荐 **1 个**步骤。
  - 推荐前自动判断"是否能做"（剩余步骤中符合条件的），不能做就不展示。
- **交互**：用户可直接点开"顺手做"的步骤进入子流程；返回后倒计时继续。

#### 3.3.7 步骤完成与下一步
- 用户完成当前步骤 → 点击"下一步"按钮。
- 切换动画：**横向滑动**（从右滑入），符合移动端原生体验。

#### 3.3.8 退出与恢复
- 用户中途退出（如按返回键）→ 记录当前进度（菜 id + 步骤 index）。
- 再次进入该菜时，**直接跳转到上次的步骤**。
- 数据存储：localStorage（未登录；MVP 阶段所有用户进度都走 localStorage）。

### 3.4 结果页

#### 3.4.1 触发
用户完成最后一步后进入结果页。

#### 3.4.2 视觉元素
- **菜名 + "完成了"**：
  - 一行显示不换行（菜名过长时省略号截断）。
  - 例：`番茄炒蛋 完成了`。
- **完成图标**：
  - 半透明浅绿色背景 + 绿色对勾。
- **庆祝动画**：
  - 从上到下播放。
  - 候选方案：
    1. 彩带飘落（实现复杂时可降级）
    2. 五彩纸屑爆炸
    3. 简单放大缩放 + 星星粒子
  - **MVP 选 3**（简单放大缩放 + 星星粒子）即可，复杂动效留作迭代。
  - 动画时长：1.5 ~ 2.5 秒。
- **剩余菜品**：
  - 展示还没做的菜，用**与方案页相同的菜品卡片样式**。
  - 用户可点击直接进入教学。
  - 若全部完成 → 显示"今天的开饭搞定啦 🎉"。

### 3.5 缓存策略

| 内容 | 缓存位置 | 失效时机 |
|------|---------|---------|
| 生成的菜谱方案 | 后端 Redis + 前端 Pinia | 用户点击"换一批菜" |
| 菜谱的步骤详情 | 后端 Redis（按 dish_id） | 永不失效（或 LRU 30 天） |
| 食材识别中间结果 | 不缓存 | 一次性 |
| 用户输入的原始图片/文本 | 对象存储（OSS） | 长期保存（用于追溯） |
| 倒计时状态 | localStorage | 倒计时结束 |
| 用户进度 | localStorage | 完成后归档 |
| 历史记录（方案列表） | localStorage | 浏览器清数据时清空 |

> **MVP 阶段不做登录**，所以用户维度的数据（历史记录、进度、倒计时）全部走 localStorage。后续接入登录后再迁到后端数据库。

**关键原则**：
- 切回方案页时**不重新请求**，直接展示已缓存的方案。
- 只有点击"换一批菜"才重新调用 LLM。
- 卡片切换**不能闪动**（避免 v-if + 重渲染导致的闪烁），技术实现上采用 `v-show` + 数据响应式切换。

---

### 3.6 账号与登录

#### 3.6.1 MVP 阶段
**MVP 不做登录**。用户所有数据（历史记录、当前进度、倒计时状态）保存在浏览器 localStorage。

**不登录的代价（提前说清）**：
- 用户换浏览器、清缓存数据，历史记录和进度会丢失。
- 倒计时无法跨设备同步（只在本机生效）。
- 用户首次进入直接是主页，不需要任何认证流程。

#### 3.6.2 后续接入登录（v1.1+）
登录方式（**待 v1.1 阶段决策**）：
- 推荐：**手机号 + 短信验证码**（最符合手机端用户习惯）。
- 备选：微信 OAuth / 邮箱 + 密码 / 一键登录（运营商网关）。

#### 3.6.3 数据库设计（仅 MVP 后端需要）
- **PostgreSQL**：MVP 阶段主要用于**服务端 LLM 输出缓存**（菜谱方案、步骤详情）。
  - 不需要用户表、用户偏好表（无登录）。
  - 表结构：`schemes`、`dishes`、`dish_steps`、`llm_cache`（用于去重和限流）。
- **Redis**：
  - 缓存 LLM 输出（按 hash 键去重）。
  - 限流（防刷，每个 IP / session 限频）。
  - 任务队列（如使用异步任务）。
- **对象存储（阿里云 OSS）**：用户上传的图片。

### 3.7 异常处理

| 异常场景 | 用户感知 | 处理方式 |
|---------|---------|---------|
| 上传图片过大 | 提示"图片超过 10MB" | 弹窗 + 重选 |
| 上传图片格式不支持 | 提示"请上传 jpg/png 格式" | 弹窗 + 重选 |
| 上传超过 5 张 | 提示"最多 5 张" | 弹窗 + 重选 |
| 网络错误 | 提示"网络开小差了，重试一下" | 重试按钮 |
| LLM 调用超时（>5 分钟） | 提示"AI 想得有点久，重试一下" | 下方出现"重试"按钮；**不显示**"换一批菜" |
| LLM 识别出食材占比异常 | 提示"截图好像没看到具体食材" | 按钮变为"上传/手动/语音" |
| LLM 输出格式异常（解析失败） | 重试一次；仍失败则提示 | 内部告警 |
| 倒计时被清后台 | 无感知 | 根据结束时间戳重算 |

---

### 3.8 请求超时
- **超时阈值**：5 分钟（300 秒）。
- **触发**：
  - 超过 5 分钟未返回 → 前端展示重试按钮。
  - 重试按钮位置：原 loading 区域下方。
  - 重试按钮存在期间**不显示**"换一批菜"按钮（因为方案还没出来）。
- **后端配合**：
  - 后端应设置稍大于前端的超时（如 310 秒），避免后端先超时返回错误。

## 4. 非功能需求

### 4.1 性能
- 页面首屏 < 1.5s（移动端 4G）。
- LLM 响应时间（用户感知）：< 30s 加载动画应"持续思考感"，> 30s 应有"还在努力"提示。
- 切换页面、切换菜品无白屏。

### 4.2 兼容性
- iOS Safari 14+、Android Chrome 80+、微信内置浏览器。
- 不支持 IE。
- 移动端竖屏为主，**不做横屏适配**。

### 4.3 安全
- 图片上传走对象存储，URL 不长期暴露。
- 短信验证码 5 分钟有效，1 分钟内同号不重发。
- API 走 HTTPS，JWT 鉴权。
- LLM 提示词注入防护：用户输入与系统 prompt 严格分离。

### 4.4 隐私
- 用户上传的图片仅用于本次生成，30 天后自动清理（可在偏好里关掉）。
- 不收集用户位置等无关信息。
